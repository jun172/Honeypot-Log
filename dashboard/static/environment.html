1. システムの目的と全体概要

Stateful Decoy & AI Telemetry

本システムは、世界中のサイバー攻撃を安全なクラウド隔離型ハニーポットに誘い込み、攻撃者の手口やマルウェア配布URL（C2インフラ）を自動採取し、AI/MLでリアルタイムに可視化する脅威インテリジェンス基盤です。

単なる静的ログ記録にとどまらず、攻撃ボットの生存確認やフレームワーク特有の応答をメモリ上で動的にエミュレートする「ステートフル高対話風ハニーポット（honeypot.py）」と、その構造化ログを解析・可視化する「AI異常検知ダッシュボード（Honeypot-Log）」が連携します。プロジェクト honeypot-515503 上の仮想マシン hp-vm-us-01（ゾーン: us-central1-a / Container-Optimized OS）では、hp-allow-honeypot-8080 による80個の罠ポート受付と、多層隔離・外向き通信遮断・GitHub/Cloud Build連携による安全な自動更新を組み合わせ、外部への踏み台化を抑止しながら高精度な観測データを収集します。

2. 最新5ブロック構成アーキテクチャとCI/CD連携

80 Ports / Read-Only / CI/CD
図1：最新5ブロック構成（80罠ポート誘致・多層隔離・ログ集約・AI/ML可視化・CI/CD自動デプロイ）

① 攻撃の誘致層（80個の罠ポート構成）

ファイアウォールルール hp-allow-honeypot-8080 により80個のポートをVM（hp-vm-us-01）へ誘導します。標準・代替HTTP/Proxy（43ポート：80, 443, 8080, 3128 等）、開発フレームワーク・管理パネル（21ポート：3000, 5000, 8069, 9200 等）、DB・キャッシュ（7ポート：3306, 5432, 6379, 27017 等）、IoT・ルーター・カメラ（9ポート：554, 7547, 8291, 37777 等）をカバーし、管理用SSH（22番）はGoogleのIAPサーバー（35.235.240.0/20）のみへ限定します。

② 多層隔離層（--read-only / iptables / hpuser）

  • コンテナ厳格隔離: ファイルシステム書き込み禁止（--read-only）、全Linuxケーパビリティ剥奪（--cap-drop=ALL）、非特権ユーザー hpuser 実行、メモリ256MB制限・pids-limit=128、内部ネットワーク hp-internal を組み合わせます。
  • SSRF・外向き通信遮断: iptables によるGCPメタデータサーバー（169.254.169.254）へのSSRFブロックと外向き通信遮断に加え、VPCの hp-deny-all-egress（および PGA 199.36.153.8/30 TCP 443 制御）で外部踏み台化を防ぎます。
  • 動的エミュレーション＆パケット録画: honeypot.py が攻撃応答を動的に返し、Base64/Hex復号やIOC（URL・IP）抽出を行い、tcpdump 等で .pcap 録画を取得します。

③ ログ集約・保全層（Cloud Logging ＆ Cloud Storage）

コンテナが出力する構造化JSONログ（攻撃分類、復号ペイロード、抽出URLなど）は Cloud Logging（gcplogs）へリアルタイム集約され、録画したパケットデータ（.pcap）は Cloud Storage バケット（gs://honeypot-archive-515503）へ長期保管されます。

④ AI/ML 可視化 ＋ ⑤ CI/CD 自動デプロイ層

収集ログは IsolationForest による異常度スコア算出や攻撃クラスタ分類を経て、SSE（Server-Sent Events）で3秒ごとにダッシュボードへ配信されます。また、ローカルから git push（jun172/honeypot）すると Cloud Build が Docker イメージ（honeypot-http / hp-nginx）をビルドして Artifact Registry（asia-northeast1-docker.pkg.dev）へ格納し、VMメタデータ更新と再起動でSSH不要の自動更新を行います。

ポート同期に関する運用メモ： ファイアウォール側（hp-allow-honeypot-8080）が80ポート開放状態であっても、VM（hp-vm-us-01）の起動時刻や startup.sh の反映状態によってはコンテナ側待ち受け数が旧構成（45ポート等）のままとなる場合があります。startup.sh（80ポート版）の git push とVM反映・再起動を行うことで、ファイアウォールとコンテナの待ち受けポート数を一致させることができます。

3. 対応できる攻撃・対象外の攻撃（設計上の割り切り）

Threat Coverage

得意な攻撃（HTTP/HTTPS・主要80ポート上のスキャン＆エクスプロイト）

  • IoT・ルーター乗っ取り（Mirai系 / Mozi系）: 生存確認への動的応答やアーキテクチャ不一致（Exec format error）の擬似応答により、攻撃者が保持する複数CPUアーキテクチャ向けマルウェア配布URL（http://<IP>/...）を引き出します。
  • 最新Webフレームワーク RCE: Next.js Server Actions（next-action）、Laravel / PHPUnit（eval-stdin.php / .env 探索）、ThinkPHP、Spring Boot（/actuator/env）、Jenkins（/script）などの脆弱性プローブに対し、本物に近い偽応答を返して後続ペイロードを観測します。
  • ヘッダ経由攻撃・Web/DBスキャン: Log4j（${jndi:ldap://...}）や Shellshock 等のヘッダ注入、SQLインジェクション、XSS、パストラバーサル（偽 /etc/passwd）、WordPress総当たり、オープンプロキシ探索を全ヘッダ走査とBase64/Hex自動復号で捉えます。

対象外の攻撃（安全な設計上の割り切り）

  • 非HTTP専用バイナリプロトコル: SSH（22番）そのものへのログイン対話や、SMB・RDP等の専用バイナリプロトコルハンドシェイクは対象外です（管理用SSHはIAP経由に限定し、一般公開は閉鎖）。
  • 実際のOS破壊や外部への踏み台攻撃: 攻撃コマンドの実行や外部ネットワークへの自由な送信を遮断しているため、本システムが踏み台となって他社へDDoSや外部攻撃を仕掛けることは構造的に抑止されています。

6. 今後の課題と拡張ロードマップ

Roadmap: Phase 2 & Phase 3

現在は「安全に攻撃を観測・可視化するフェーズ（Phase 1）」を達成しており、今後は検体自動保全（Phase 2）やプロトコル特化・AIサーバー狙いデコイへの拡張（Phase 3）へ発展させる計画です。

主な課題

  • 非HTTPバイナリプロトコルの対話不足： DB系（3306, 6379, 27017）や RTSP（554）等もHTTP待ち受けへ集約しているため、専用バイナリプロトコルを前提とするボットは途中で切断する場合があります。
  • 捕獲URLから検体取得・解析までの手作業： ログからマルウェア配布URLを抽出するまでは自動化済みですが、配布サーバーが消える前に検体（ELFやスクリプト）を自動取得し、REMnux（floss / Ghidra / YARA）へ渡す工程は改善余地があります。
  • Webシェル設置後など高度なステートフル対話の深化： バックドア配置後の再アクセスや後続ステージの挙動をメモリ上でより深く擬似再現する拡張が考えられます。
  • TLS/HTTPS（443 / 8443）通信への対応： 暗号化ハンドシェイクを最初から要求するスキャナーやツールからの通信も観測できる余地があります。

1. Purpose & System Overview

Stateful Decoy & AI Telemetry

This system is a cloud-isolated threat intelligence honeypot platform that lures external cyberattacks into a hardened environment, extracts attacker techniques and malware distribution URLs (C2 infrastructure), and visualizes activity in real time using AI/ML.

Beyond passive request logging, it pairs a stateful high-interaction-style HTTP decoy (honeypot.py) that emulates bot liveness checks and framework responses in memory with a real-time AI anomaly detection dashboard (Honeypot-Log). Deployed on Compute Engine instance hp-vm-us-01 (zone: us-central1-a / Container-Optimized OS) in project honeypot-515503, the platform combines 80-port firewall exposure (hp-allow-honeypot-8080), multi-layer container/network isolation, egress blocking, and GitHub/Cloud Build CI/CD to collect rich telemetry while preventing outbound pivot risk.

2. Five-Block Architecture & CI/CD Pipeline

80 Ports / Read-Only / CI/CD
Figure 1: Five-Block Architecture (80 Lure Ports, Multi-Layer Isolation, Log Retention, AI/ML UI, and CI/CD)

1. Attack Lure Layer (80 Exposed Ports)

Firewall rule hp-allow-honeypot-8080 directs 80 ports to VM hp-vm-us-01 across web/proxy (43 ports: 80, 443, 8080, 3128, etc.), dev/admin panels (21 ports: 3000, 5000, 8069, 9200, etc.), databases/caches (7 ports: 3306, 5432, 6379, 27017, etc.), and IoT/routers/cameras (9 ports: 554, 7547, 8291, 37777, etc.), while SSH (port 22) is restricted to IAP (35.235.240.0/20).

2. Multi-Layer Isolation (--read-only / iptables / hpuser)

  • Hardened Container: Combines read-only rootfs (--read-only), dropped capabilities (--cap-drop=ALL), non-root user hpuser, 256MB memory limit, pids-limit=128, and internal network hp-internal.
  • SSRF & Egress Controls: Uses iptables to block metadata SSRF (169.254.169.254) and outbound traffic alongside VPC rule hp-deny-all-egress (with PGA 199.36.153.8/30 TCP 443).
  • Stateful Decoys & PCAP Capture: honeypot.py returns dynamic responses, decodes Base64/Hex payloads, extracts IOCs (URLs/IPs), and captures packets via tcpdump.

3. Log Aggregation & Retention (Cloud Logging & GCS)

Structured JSON telemetry (attack classifications, decoded payloads, and extracted URLs) streams to Cloud Logging (gcplogs), while packet captures (.pcap) are archived in Cloud Storage bucket gs://honeypot-archive-515503.

4. AI/ML Visualization & 5. Automated CI/CD

Logs undergo IsolationForest anomaly scoring and attack clustering, streaming every 3 seconds via SSE to the dashboard. Pushing to GitHub (jun172/honeypot) triggers Cloud Build to build honeypot-http and hp-nginx images in Artifact Registry (asia-northeast1-docker.pkg.dev) and update/restart the VM without public SSH.

Port Synchronization Note: Even when firewall rule hp-allow-honeypot-8080 permits 80 ports, active container listening ports on hp-vm-us-01 may reflect an earlier boot (such as 45 ports) until the 80-port startup.sh is pushed via git push and applied on the VM.

3. Attack Coverage & Design Boundaries

Threat Coverage

Supported Attack Vectors (HTTP/HTTPS & 80 Lure Ports)

  • IoT & Router Botnets (Mirai / Mozi): Responds dynamically to liveness checks and simulates architecture mismatch errors (Exec format error) to elicit multi-architecture malware download URLs (http://<IP>/...).
  • Modern Framework RCEs: Emulates realistic responses for probes targeting Next.js Server Actions (next-action), Laravel/PHPUnit (eval-stdin.php / .env), ThinkPHP, Spring Boot (/actuator/env), and Jenkins (/script).
  • Header Exploits & Web/DB Scans: Scans all headers and auto-decodes Base64/Hex for Log4j (${jndi:ldap://...}) or Shellshock, alongside SQL injection, XSS, path traversal (decoy /etc/passwd), WordPress brute-force, and open-proxy probes.

Out-of-Scope & Safety Boundaries

  • Non-HTTP Binary Protocols: Interactive SSH logins on port 22 or dedicated binary handshakes for SMB/RDP are outside HTTP decoy scope (management SSH is restricted to IAP).
  • OS Compromise or Outbound Pivot: Blocking arbitrary command execution and outbound connections prevents the honeypot from being used as a pivot or DDoS launchpad.

6. Future Challenges & Expansion Roadmap

Roadmap: Phase 2 & Phase 3

Having established safe observation and real-time visualization (Phase 1), the platform can evolve toward automated sample collection (Phase 2) and protocol- or AI-target-specific decoys (Phase 3).

Current Challenges

  • Limited Non-HTTP Binary Interaction: Database (3306, 6379, 27017) and RTSP (554) ports currently feed HTTP listeners, so binary-native clients may disconnect early.
  • Manual Sample Retrieval & Analysis: Extracted malware URLs are logged automatically, whereas fetching binaries before C2 takedown and analyzing them in REMnux (floss, Ghidra, YARA) can be further automated.
  • Deeper Post-Exploitation State: Simulating multi-step post-access behavior (such as revisiting uploaded web shells) in memory offers room for richer interaction.
  • TLS/HTTPS (443 / 8443) Coverage: Clients requiring TLS handshakes from the start are not yet terminated over HTTPS.
